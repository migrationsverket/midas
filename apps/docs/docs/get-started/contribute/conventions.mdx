# 🌿 Commits och release

## 📝 Commits

Vi följer [conventional commits](https://www.conventionalcommits.org/en/v1.0.0/#summary). Nya versioner och changelog skapas automatiskt från commit-meddelandena, så formatet spelar roll. Skriv på engelska i imperativ form, och låt scope börja med det Nx-projekt som ändras:

```bash
feat(components,button): add new button variant   # minor
fix(theme): fix button hover color                 # patch
docs: update contribution guide                    # ingen ny version
```

En breaking change markerar du med `BREAKING CHANGE:` i commit-meddelandets body, och då blir det en ny major-version.

:::warning
Ta aldrig bort funktionalitet direkt, deprecera först! Markera med `@deprecated` i koden och dokumentera i release notes. Ge användare minst en major-version att migrera innan borttagning.
:::

## 🚀 Release

Allt som mergas till `main` släpps automatiskt. Nx Release räknar fram nya versioner från commit-meddelandena, publicerar till npm, uppdaterar changelog och bygger om dokumentationswebben. Du behöver inte göra något själv.

### Paket på version 0.x

Så länge ett paket har version 0.x följer Nx Release SemVer-konventionen för instabila versioner, där varje versionsändring flyttas ned ett steg: en breaking change ger en ny minor-version och `feat` ger en patch.

Det betyder att ett paket **aldrig når 1.0 automatiskt**, inte ens med en breaking change. Steget till 1.0 är ett medvetet beslut om att API:et är stabilt, och det görs manuellt med `nx release`.
